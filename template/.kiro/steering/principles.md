# 方法论信条

steering-id: PR-3031

## [P01] 把教训编码进结构（encode-lessons-in-structure）

**适用**：用户纠正你、测试失败或结论被推翻、或你发现自己在第二次写同一条提醒时。

**为什么**：文字提醒要读者注意到、记住、照做，容易漏；光说"我会注意"不跨会话。教训要落进持久文件，并在该用时被认出来。

**做法**：
1. **先查（回答或动手前必做，不能跳过）**：对照常驻的踩坑索引 `lessons-index.md`。当前问题落在任一条的"何时"里，不管是你自己要下的判断，还是用户提出的结论或提问，都要先读 `docs/lessons/lessons.md` 对应条目全文再作答。索引没覆盖、但属于下结论、诊断归因、方案选择的，grep `docs/lessons/lessons.md`（场景词 / 报错特征 / 方案名）。
   - 失败示例：用户拿两组小样本对比数据（如"方案 A 命中 0 次、方案 B 命中 0 次"）问你"是不是说明两者没差别"，没查对应 lesson 就直接作答，漏掉了零假设概率和样本量要求。
2. **记录**：每次被纠正都判断是一次性还是同类 → 在 lessons.md 新增条目（计数 = 1，同时在 `lessons-index.md` 加一行）或给同类条目计数 +1。计数只记 agent 没查到或没用上而重犯的情况；成功拦下的（包括拦住用户提出的错误结论）不计数。你写草稿，用户确认后落盘；条目带证据出处（文件:行）。
3. **闭环**：当场修掉，或建一个具体待办；只记录不行动等于没记。某条计数在涨，说明它没被认出来——改进它在索引里的"何时"描述和关键词。

**反模式**：口头承认不落盘；只修这一处，不处理同类。

## [P02] 证明它真的成了（prove-it-works）

**适用**：宣布"完成 / 修好了 / 已生效 / 确认了"之前，以及报告任何"我验证过"的结论前。

**为什么**：没验证的工作正确性未知；最常见的失误不是没去查，而是查完之后在报告里把推测说成了事实。

**做法**：
1. 验证这次的目标本身：直接触发 / 观察本次的行为或数据；退出码 0、"测试全绿"、标签写着 success 都不算证明。打真实外部服务需用户明确同意。
2. 结果反常或对不上时，先怀疑观察方法（看错了地方？读的是缓存？工具没显示？），再怀疑系统。
3. 报告时分开写：**观察到的**（命令 + 关键结果，数字照实抄）和**推测的**（明确标"未验证"）；没验证的部分写明原因。对字段、状态、行为含义的解释，要么给出处（代码 / fixture / 文档 / 命令输出），要么标"未验证 / 推测"；查不到出处就别补成事实。

**反模式**：把自己的预期当观察结果（例："两次数据一致是正常的，不是缓存问题"——没验证就断言）；转述数字时凭印象写；用"测试都通过了"代替检查这次改动。

## [P03] 先定数据结构（foundational-thinking）

**适用**：写新逻辑、加新功能或模块、改动跨多个函数或文件之前。单行修复、改文案、改配置值不适用。

**为什么**：结构性决策保住选择余地，代码级决策保住简单。数据形状定对了，下游代码自然就简单；先写逻辑再补结构，会把对形状的假设散落到各处的条件分支里。

**做法**：
1. **数据结构先行**：动手前先说清这次的核心数据形状——用到或新增哪些类型、主要访问路径是什么，选匹配主路径的结构。
2. **脚手架先行**：对后续每一步都有益的东西先做（共享类型、测试 fixture、lint、CI）；先搭再做功能，先有测试再修。有死代码先删再搭。提交保持小而单一目的。
3. **每一步落下一个完整的抽象，或深化已有的**；不要把新能力摊成各调用方里的特例协调。
4. **代码级**：结构去重（类型和模型收敛到一处），代码行不强求去重——三段相似的代码胜过过早抽象；显式胜过巧妙；测行为和边界，不追行数。
5. **并发推论**：多线程共享状态之前，先问"另一个线程同时改它会怎样"；答案不是"没事"就隔离。

**反模式**：先写一堆 if/else 再回头补类型；同一个形状在多个文件里各定义一遍；为只有一处用法的地方新建抽象层。

## [P04] 用最少的代码解决（laziness-protocol）

**适用**：重构或"改进"代码、评估改动大小、想加抽象或层、或要把新信号穿过多层时。

**为什么**：用最少的代码和复杂度拿到最多的结果。细小的泄漏和重复的选择会扩散，最后变成长期的协调成本。

**做法**：
1. **优先删除**：被要求重构或改进时，先找能删的，再考虑加。
2. **调用层级扁平**：避免深调用链；藏住大量实际工作的丰富接口不算深链。回答一个问题要追超过 3 个文件或层，就把它压平。
3. **决策收敛**：同一个选择不要在多处重复做；收到一个真相源，把结果当简单 flag 传下去。
4. **diff 最小**：用能解决问题的最小改动；行数少胜过"优雅"的样板代码。
5. **质疑穿透**：任务要你把一个新信号穿过类型、schema、管线等多层时，先停下来找更直接的路径。
6. **小泄漏早处理**：细小的透传、表示泄漏、重复的选择，在扩散前清掉。

**检验**：人类开发者维护起来觉得累的代码，就是坏方案。

**反模式**：为只用一次的逻辑抽 helper / util；为"看起来健壮"加不会触发的防御代码；用 try 包裹不会抛异常的代码；调用方不需要区分处理时仍为每种错误建自定义异常类。

## [P05] 修根因，不修症状（fix-root-causes）

**适用**：调试时——报错、崩溃、测试失败、行为不符合预期，需要定位并修复。

**为什么**：症状修复会累积。每个变通都让系统更难推理，真正的 bug 还在。修根因前期慢，但总调试时间更少。

**做法**：
1. **先复现**：能写成失败测试的，先写一个能复现 bug 的失败测试。
2. **追问"为什么"直到根因**，修在根因处。
3. **不加守卫**：加个 None 判断让崩溃消失，是症状修复。
4. **变通需要一大段注释来辩护，说明代码错了**：改代码，不是改注释。
5. **查同类模式，不只修这一处**：grep 同样的模式，全部修掉。
6. **卡住时加观测，不猜**：加日志、读真实报错。

**重启类 bug：先疑状态，后疑代码**：某个东西"重启后就坏了"，先怀疑过期的持久状态——配置文件、缓存、锁文件、序列化状态。清掉某个状态文件行为就恢复的，优先把状态校验作为修复。

## [P06] 测行为，不测实现（test-behavior-not-implementation）

**适用**：写、改或决定保留一个测试时。

**做法**：测试按使用者的方式调用代码，把他们观察到的结果和一个字面量期望值比较。断言代码调用了什么、或复述代码里的常量的测试，两样都没做到。

**检验**：保留一个测试之前，问：如果它导入的每个函数都返回 `None`，它还会通过吗？会，说明它观察不到行为，不会因缺陷而失败——改写断言或删掉测试。

**为什么**：不会因缺陷失败的测试耗 CI 时间和 review 注意力，什么也拦不住。常量钉死的测试还会在有人改这个常量或它复述的提示词时失败，等于阻止了这次修改。

**被测函数全返回 `None` 仍会通过的五种形态**：
- **断言弱或没有断言**：没有 `assert`，或只有 `assert x`、`is not None`、`isinstance(...)`、`> 0`、只验证不抛异常。
- **只断言 mock 或"不存在"**：只有 `assert_called*()`、`assert_not_called()`、`is None`、`== []`、`len(...) == 0`、`!= 错误值`。
- **自我引用**：期望值来自被测代码：`assert f(a) == f(a)`、`assert parsed.url == build_url(...)`。
- **常量钉死**：断言复述手工维护的常量、配置默认值、表格行或提示词：`assert LIMITS["max_tools"] == 8`、`assert "You are" in PROMPT`。
- **fixture 断言 fixture**：断言读的是测试自己构造的数据或 fixture 里算好的值，被测对象根本没在测试体内运行。

**修法**：在测试体内用一个具体输入调用被测对象，断言字面量输出或可观察的效果，如 `assert slugify("Hello, World!") == "hello-world"`。要断言"不存在"，就在同一个测试里对另一个输入断言"存在"。对常量，用一个输入测读取它的机制，而不是复述它的值。对 mock，断言它收到的参数或调用后的状态，而不是"被调用过"。找不到这样的断言，就删掉测试。

**保留**：跨表格行的关系测试（某个 key 同时出现在两张表、父项存在），以及编译期类型检查测试。

## [P07] 改旧前先上锁（lock-before-changing）

**适用**：动手修改已有代码之前——重构、修 bug、在已有模块里加功能。新建的独立文件不适用。

**为什么**：改已有代码最常见的失败，不是改错了目标，而是悄悄弄坏了别处依赖它的行为。改之前没有一个跑通的验证，改完就无从判断坏没坏。但"锁住现有行为"并非对所有改动都对：修 bug 时锁住现有行为，等于把 bug 也锁死了。

**做法**：
1. **按改动类型定验证**：行为不该变的（重构）→ 先写测试锁住现有行为，改之前必须是绿的；行为要变的（修 bug、加功能）→ 先写描述目标行为的测试（修 bug 时先红后绿），不锁要被改掉的行为。
2. **查波及**：列出这次要改的函数、类、共享状态，往上追一层调用方。被本次改动之外的代码依赖的路径，先锁住它的现有行为再改——加功能时也一样，这是最容易漏的。
3. **为可测而做的重构要小**：只限搬移、改名、抽取这类一眼可见安全的改动；超出这个范围 → 停下问我。
4. **没有合适的切入点就不硬写**：找不到能测到真实行为的位置时，不为了"有测试"去写一个测不到问题的测试；说明这块是高风险区，并提议登记可测试性债（`/td-tech-debt`）。

**反模式**：修 bug 前先给现有的错误行为拍快照测试；只测新功能，不管顺手改到的共享代码；在浅层切入点写一个通过了也证明不了什么的测试。

**与其它信条的关系**：修 bug 的"先红后绿"即"修根因"的第 1 步（先复现）；测试怎么写见"测行为，不测实现"。本条多出的是两件事：**按改动类型选择锁什么**，和**改之前查波及**。

## [P08] 减轻读者负担（minimize-reader-load）

**适用**：review 或塑造难以追踪的代码时；准备加一层或加一份状态之前。

**为什么**：可维护性 = 读者理解代码要做的功。代码被读的次数远多于被写；行数、圈复杂度、"整洁架构"都只是代理指标，读者负担才是本体。两个轴相互独立：一个有 50 个全局变量的平铺文件，和一个 6 层的适配器栈一样难推理，两个都要守。读者的工作记忆也是有限的。

**盯两个轴**：
1. **要追的层数**：问题和答案之间隔了多少层间接。
2. **要记的状态**：读者得在脑子里记住多少隐藏的或可变的上下文。

**做法**：
- **压掉得不偿失的层**：只有一个调用方的包装、没有第二个实现的适配器、从没用上的投机性间接——内联掉。
- **相邻层必须改变抽象**：重复同样方法和参数的层只增加负担、不做压缩；压掉透传层。
- **要求接口有压缩比**：宽接口却藏不了多少复杂度，读者得同时学表面和实现。优先选能藏住有意义决策的边界。
- **缩小状态作用域**：优先纯函数（返回值优于修改），局部变量优于字段，字段优于模块状态，模块状态优于全局。能推导就别同步。
- **在边界处点明不变量**，而不是在每个使用方里，让读者只学一次。
- 加一层或加一份状态之前先问：它在别处减少的读者负担，至少有这么多吗？

**检验**：新读者能在 30 秒内回答"X 从哪来？"和"什么能改变 X？"吗？不能，就砍层或砍状态。

**反模式**：写复述代码的注释（`# 获取用户` 后跟 `get_user()`）；一个文件里混多个不相关的导出；把配置、常量、类型、工具函数都堆进 `utils` / `helpers` 垃圾抽屉。

## [P09] 守在边界（boundary-discipline）

**适用**：接入校验、错误处理或框架适配代码时。

**做法**：校验、类型收窄和错误处理放在系统边界；内部代码无条件信任。业务逻辑放在纯函数里；外壳薄而机械。

**为什么**：散落的校验嘈杂、冗余，还给人虚假的安全感。把逻辑留在框架接线之外，才能脱离框架测试它。

**模式**：
- **在边界上**（CLI 参数、配置文件、外部 API、网络协议）：校验、返回错误、防御性处理。
- **在系统内部**：类型化数据、错误向上传播、不重复校验。信任类型。
- **跨边界时**：暴露领域概念，而不是边界的私有表示。通用机制放里面，专用策略放边缘。

**应用**：
- 在解析时（边界）校验配置，而不是在业务逻辑里。
- 在边界把原始数据解析成领域类型。
- 不要通过公开接口再导出传输、存储、框架或线上格式的类型。
- 边界已经校验过的，调用链深处不要再加冗余的 None 检查。
- 业务逻辑放在不依赖框架的纯函数里；解析函数 = 从原始字节到类型化状态的纯变换；提示词构造 = 结构化状态进、字符串出；打分评估 = 从状态到结果的纯变换。

**检验**：
- "这份数据此刻正在穿过系统边界吗？"不是，校验就是冗余。
- "这能不能是一个外壳只管调用的纯函数？"能，就抽出来。

## [P10] 先减后加（subtract-before-you-add）

**适用**：安排一次新增、重构或重写的**顺序**时。

**做法**：
1. **删除排在构造之前**：动手加之前，先删死代码、冗余校验、空 stub 引用，在更简单的基座上再建——基座更小往往让接下来的设计一目了然。
2. **先砍到最小，再打磨**：先到达能用的最小形态，再投入打磨质量；别在还会被删的东西上先追求优雅。
3. **引用无新内容就删掉**，不要留一个空 stub。

**检验**：收尾时系统比你接手时更简单、能力不减、对外表面不增，就对了。

**与其它信条的关系**（不重复展开）：
- "优先删除""最小 diff" → 见 laziness-protocol。
- "不加 spec 没要求的臆测校验器/parser/guard""为观察到的用法设计、不为臆测边界" → 见 laziness-protocol 反模式与 boundary-discipline。
- 本条只多一个维度：**排序**——先减再加，而非一边加一边想着以后再删。

## [P11] 让非法状态无法表示（type-system-discipline）

**适用**：设计类型、审一个函数签名、或在任何静态类型语言里写代码时。跨语言成立；具体语法按项目语言取用。

**内核**：类型检查器是证明助手——用它在"能证明的时候"消除不可能的状态、错配的基本类型、未处理的变体。能被类型挡在编译期的错，别留成运行时失败。优先把错误和特例"定义掉"，而不是堆处理器。

**做法（信条，语言无关）**：
1. **非法状态不可表示**：用和类型（sum type）建模变体，别把状态塞进一堆可选字段、让矛盾组合也能编译。`{completed: bool, completedAt?}` 允许 `completed=true` 却无时间——无意义。改为从单一来源派生，或显式建模变体。若 debug 时冒出"这组合到底会不会发生？"，说明类型太松。
2. **类型是构造，不是限制**：从想要的值把类型搭起来，而不是从更松的类型里用检查抠出来。非空列表 = 头 + 尾，不是"带长度检查的列表"；合法时间段 = 起点 + 时长，不是"两个要保持有序的时间戳"。选那个**造不出非法值**的形状，再在上面暴露调用方要的接口。
3. **语义基本类型加品牌**：`UserId` 和 `OrderId` 底层都是字符串，但不该可互换。创建时校验一次，之后信类型。
4. **外部数据在解析前是无类型的**：RPC/JSON/IPC/CLI 参数/配置/环境变量/数据库行——每个边界放一个 parse 函数，把非结构化输入变成类型化模型（校验放哪见 boundary-discipline）。
5. **不骗类型系统**：cast、不安全强转、绕过检查器的断言函数都是潜伏的运行时崩溃。检查器证明不了的事，要么去证明（校验/收窄/改模型），要么承认这个 cast 是隐患。
6. **穷尽变体是检查器的职责**：对和类型做匹配时，新增变体却没处理应当编译失败。用语言提供的习语（TS 的 `never` 绑定、Rust 未加注解的 `match`、Haskell `-Wincomplete-patterns`、Kotlin sealed-class 穷尽）。
7. **只在"部分性"出现处加强类型**：一个运行时断言 / None 检查 / "这不该发生" 的 throw，标记着类型太弱的位置——把这个检查上推进类型，然后**停**。类型系统的职责是追踪每个使用点必须处理的情形，不是把数据描述到极致。优先全函数：空列表求和是 0（吃普通列表），空列表取头无解（要求非空列表）。

**检验**：
- "我能写注释解释这组字段何时合法吗？"能 → 类型太松，拆成和类型。
- "两个函数参数共享基本类型却含义不同吗？"是 → 加品牌。
- "这个 `any` / `as` / `assertNotNull` 从哪来？"追到边界，在那里校验。
- "下月加个新变体，检查器会告诉下一个 agent 在哪补 case 吗？"不会 → 匹配不穷尽。
- "这个类型在重复另一个文件拥有的 shape 吗？"是 → 派生，别手搓（见 encode-lessons-in-structure）。
- "我加强这个类型是为保一个操作全函数，还是只为更精确？"若没有东西会 panic，保持普通类型。

**动态类型语言的前提**：项目若不跑静态类型检查器（如未配置 mypy/pyright、未开启等价的类型检查），则"不骗类型系统""穷尽匹配靠编译失败""编译期证明"这类条款在引入静态检查器之前为可选 / 不适用。运行时边界校验（如 pydantic 等运行时校验库抛异常）与编译期证明互补——"过了运行时校验"不等于"类型被编译期证明了"，别混为一谈。

## [P12] 让操作可以重复执行（make-operations-idempotent）

**适用**：设计在崩溃、重启、重试中运行的命令、生命周期步骤、处理循环时。

**内核**：把操作设计成——不管运行几次、从哪里开始，都收敛到同一个正确的终态。每个会改状态的操作都要能回答："如果它跑两次会怎样？如果上一次跑到一半崩了会怎样？"

**为什么**：命令、生命周期操作、处理循环运行的环境里，崩溃、重启、重试是常态。如果残留的半截状态会改变下一次运行的结果，那每次重启都变成一场 debug。

**做法**：
1. **收敛式启动**：启动时扫描已有状态——清掉过期产物、接管仍存活的会话，而不是假设干净起点。
2. **按内容清理，不按创建顺序**：判断"该不该清"用内容等价性，别靠时间戳/创建先后。
3. **自愈的锁**：用基于 PID 的过期锁检测（持锁进程已死就能安全抢占），别让一把崩溃时留下的锁永久卡死后续运行。
4. **幂等的调度**：失败的工作能干净地重新派发；每轮结束后新鲜输入重新生成，不复用可能半旧的。
5. **写状态文件要原子**：先写临时文件再 rename（同一文件系统上 rename 原子），别直接覆盖目标——否则写到一半崩溃会留下截断/损坏的文件。

**检验**：
1. 连着跑两次会怎样？
2. 上一次在每一个可能的点崩溃，分别会怎样？
3. 重跑是否收敛到同一终态？
任何一个答案是"取决于上次留下了什么状态"，这个操作就需要一个对账（reconciliation）步骤。

## [P13] 先拆分，再串行化共享状态（separate-before-serializing-shared-state）

**适用**：多个并发执行者可能写同一个文件、分支、key 或状态对象时。

**内核**：并发执行者可能共享可变状态时，**先问它们是不是真的需要同一个可变对象**。不需要就消除共享。确实需要共享时，才用结构化手段串行化访问（锁文件、串行阶段、独占所有权、原子 compare-and-swap）。**"指令和约定"不是并发控制**——靠注释/文档说"大家记得按顺序写"挡不住竞态。

**为什么**：对共享状态的并发写会制造竞态——间歇出现、难复现、调试昂贵。

**做法**：
1. **识别共享可变状态**：两边都读写的文件、都 push 的分支、一边定义一边消费的 API/结构。
2. **默认：消除共享的写入目标**。问：这些执行者需要一个规范的共享对象，还是各自在发布独立的事实？给每个执行者**自己拥有**的文件 / key / 分支 / 状态目录，只在**读/汇报的边界**合并。两个 worker 各自往同一个 `state.json` 写自己的 `lastX` 字段，仍然是共享可变；`indexer-state.json` + `metrics-state.json` 才不是。
3. **只有当"单一共享写入目标"是一个真正的不变量时，才结构化串行化**（锁文件、串行阶段、单写者 actor、原子 CAS）。把"我们需要一把锁"当成一个要去核查的设计异味，而不是默认答案。

## [P14] 用结构编码领域（model-the-domain）

**适用**：写有状态的逻辑时，或代码大量分支、在多个文件里重复同一个 shape 假设时。

**内核**：把真实领域编码进一个数据结构，而不是散落进各处的条件判断。

**为什么**：散落的布尔、重复的 shape 假设、跨文件扩散的分支，都是意外复杂度。一个贴合领域的结构能让非法状态无法表示、删掉分支。写的时候选它很便宜；事后再把它捞回来会被当成重构、于是被一拖再拖。

**可以伸手去拿的结构**：
- 状态机，替代散落的布尔 / 阶段 / 生命周期检查。
- 类型化对象/模型，替代松散参数或重复的 shape 假设。
- map / 注册表 / 查找表 / 判别联合（discriminated union），替代跨文件扩散的分支。
- reducer 或 command/event 模型，替代到处手改状态。
- 围绕"一块领域知识"组织的模块，而不是 load→validate→transform→save 这样的时序序列。**执行顺序不是所有权**。
- 一个小的模块边界，收拢重复的行为、所有权或不变量。
- queue / cache / index / 图/树 / 规范化集合，当数据访问模式需要时。
- 任何别的合适结构。都不合适时，先想清楚"代码绝不能允许什么" + "数据怎么被读取"，再找恰好编码这两点的结构。

**别硬抽象**：当前形状已经清晰、局部、不太会增长，就用 boring code。一个只加间接、却不删分支/不删重复规则/不消非法状态/不降生命周期风险的抽象，要怀疑。

**漏掉这条的信号**：新功能靠给既有 if/else 链再加一个分支；出现第二个必须和第一个保持同步的布尔；时序分解（按阶段命名的模块在每一步重复同样的领域规则）。

## [P15] 按第一性原理重新设计（redesign-from-first-principles）

**适用**：把新需求集成进既有设计时。

**内核**：不要把变更外挂（bolt on）到现有设计上。按"这个需求从第一天起就是基础假设"来重新设计。

**为什么**：这是把变更集成进既有设计时保住选项价值的方法。

**做法**：
1. 读完所有受影响的文件，理解当前设计。
2. 问："如果带着这个新需求从零写，我们会造出什么？"
3. 把变更传播到每一处引用：类型、文档、示例、设计理由段落。
4. 整体想清楚重设计，再增量交付。

## [P16] 造杠杆（build-the-lever）

**适用**：任何非平凡的工作，不只是批量工作——编辑、迁移、分析、检查都算。

**内核**：工作不平凡时，造一个替你做它（或证明它做对了）的工具，而不是手工去做。

**为什么**：两个收益。吞吐：codemod / 生成器 / 脚本每次都以同样方式做事，重跑免费。可信：工具是 reviewer 能读、能重跑来核对的单一产物；手工改动只能靠重做一遍来复核。确定性的脚本把"相信我"变成"跑一下这个"。

**做法**：默认造杠杆。只有任务平凡（一眼就能看清的几处明显改动）时才跳过。
- 先手工做第一个单元学会配方，再造工具；用它在那个单元上重跑、与手工结果 diff 来证明它对。让杠杆可安全重跑。
- 编辑用 codemod 或脚本，重复文件用生成器，分析用 dump 到 sqlite 再查询，验证用可重跑的检查。
- 确定性杠杆胜过分派。工具一遍能处理所有单元，就自己跑，别派子 agent 手工去做脚本能做的事。
- 要把工作分派给子 agent 时，把杠杆写成它们都读的 skill：配方、验证契约、禁碰边界放在一个产物里，并放在子 agent 写入范围之外，免得它们悄悄改契约。
- 应用这条会产出一个文件。如果你声称用了它，diff 里却没有 codemod / 脚本 / 生成器 / 子 agent skill，那你没用它。
- 工作比会话活得久时，把杠杆提交进仓库。

**平衡**：门槛是"是否平凡"，不是"是否重复"。一次性的工作，若杠杆正是让它可核查的东西，也值得造。按"用最少的代码解决"，造能完成或证明这件事的最小脚本，绝不造框架。

与"把教训编码进结构"不同：那条把反复出现的指令变成持久护栏；这条是眼前这件工作的吞吐与可复核性。脚本化验证本身见"证明它真的成了"。

## [P17] 把工作排成可验证的单元序列（sequence-verifiable-units）

**适用**：多步工作（扫一遍式修改、迁移、一串相似的编辑），以及怎么堆叠 commit 和 PR。

**内核**：把工作排成一串小单元，每个单元结束在一个能检查的状态；当前单元没变绿，就不推进下一个。

**为什么**：在引发问题的那个单元就抓到断裂，定位很便宜；一批做完才发现，断裂就被埋住了，而你已经在坏掉的基础上继续建了。把这些单元排成 reviewer 能重放的交付顺序，就把"相信我"变成"看它先红、再绿"。

**执行**：在 sweep、迁移或任何一串相似编辑里，每改一处先验证，再开始下一处。每个单元是一个前后括号：已知良好状态 → 一个改动 → 跑检查 → 再继续。先 rebase 到干净主干，让每次检查都对着真实基线。用杠杆（脚本）做编辑时，每单元检查几乎免费——照样要跑。

**交付**：按能证明工作的顺序堆 commit 和 PR。标准形态是先放失败测试，再在上面放修复。其他讲故事的顺序：先减再重塑、先采基线再施加处理、先脚手架再功能。每个 commit 能独立落地，整个序列读起来是一个论证。

与"证明它真的成了"（让每次检查是真的）和"造杠杆"（让每单元检查变便宜）互补。

## [P18] 体验优先（experience-first）

**适用**：出现产品、UX 或功能范围取舍时。

**内核**：实现上的方便和使用者的体验冲突时，选体验。宁可少发几个打磨好的功能，也不发一堆粗糙的。

**做法**：
- 每个功能、控件、选项都必须有理由。
- 少发，发好（三个打磨好的功能胜过十个粗糙的）。
- 先做原型再投入（设计决策在一次性 HTML 里比在生产代码里便宜）。
- 把细节做对（过渡、对齐、间距、反馈、错误状态）。
- 收紧核心循环（每个功能要么服务中心工作流，要么让开）。

**谁是使用者**：消费这份工作的任何人。UI 的使用者是终端用户；库或内部 API 的使用者是 import 它的同事；下一个维护代码的工程师也是使用者。同样掂量他们的体验，并从他们的角度解释影响。（过渡、对齐、间距、HTML 原型等 UI 细节条款仅 UI 项目适用。）

**与"先定数据结构"的关系**：地基要服务于体验。"先定数据结构"管工作的*顺序*，这条管*目标*。

## [P19] 攻击前提（attack-the-premise）

**适用**：两个及以上共享同一前提的修复，都没过同一道关时。

**内核**：共享同一前提的两个以上修复都没过同一道关时，怀疑前提，而不是怀疑修复。

**为什么**：共享前提下的每一次失败，都是关于这个前提的证据。

**做法**：
- **把前提写下来。** 前提就是每个失败修复都默认成立的那一句话。
- **下一个修复之前，先做普查。** 按执行者（actor）统计不平衡。普查要回答的是"不平衡落在哪些执行者身上"，而不是"不平衡有多大"。按"造杠杆"，把普查写成可重跑的脚本。
- **读出偏斜。** 如果每次都是同几个执行者占了大部分不平衡，那就是有东西把这个角色分派给了它们。找到分派角色的东西——这个分派就是按"修根因"追问的下一个"为什么"。
- **消除不对称，而不是补偿它**（按"用最少的代码解决"）。让角色在执行者之间轮换、随机化分派，或者把角色移走，使没有哪个执行者每次都拿到它。回退路径、共享池、批量交接、定期再平衡，都把分派原样留着，还让每次运行多出一份工作。

**停**：
- 前提没写下来、普查没做出来之前，不要开始下一个修复。
- 如果普查显示各执行者之间是均匀的，前提就不是原因。去别处找原因，并把普查留作证据。

与"按第一性原理重新设计"不同：那条围绕新需求重建设计；这条质疑的是当前设计默认成立的一个事实。

## [P20] 解释这个数字（explain-the-number）

**适用**：在相信、上报或依据一个你测出来的数字行动之前：提速、回退、吞吐、延迟或评测结果。

**内核**：测出来的数字是对系统的一个论断。在相信它、上报它或依据它行动之前，找出限制它的东西，并排除它测的其实是别的东西。

**为什么**：跑错了的一次运行照样会打印出一个看起来合理的数字。失败的请求、跳过了工作的缓存、根本没执行的代码、某一边停在默认配置、运行间噪声，都会产生看起来没问题的结果。如果你说不出这个数字为什么不是现在的两倍，你就不知道自己测了什么。

**做法**：
- **问"为什么不是两倍？"** 说出限制结果的资源或代码路径：某个核、某把锁、磁盘、网络，或者压测端本身。从运行期间的 profile 或系统计数器里拿到它，再映射回源码。读代码猜出来的不算限制因素。
- **列出这个数字还可能在测什么，逐一用证据排除。** 常见嫌疑：错误、被跳过或命中缓存的工作、没调优的一边、噪声、一个小到对端到端无关紧要的部分。
- **证据跟着数字走。** 把运行次数、离散程度和限制因素写进笔记或链接的产物里，让读者能核对这个论断。

对评测结果，同样追问每次试验：每次运行都真的完成任务了吗？差距在多次试验、多个模型之间都成立吗？场景本身重要吗？

**漏掉这条的信号**：数字背后的证据没有运行次数、没有离散程度、没有点名限制因素；或者省下的时间比被改动部分本身花的时间还长。

与"证明它真的成了"不同：那条检查产出是真的；这条检查测出来的数字确实是你说的那个意思。

## [P21] 穷尽设计空间（exhaust-the-design-space）

**适用**：面对代码库里没有先例的新交互或架构决策时。

**内核**：没有既定先例的新交互或架构决策，在实现之前先探索几个具体的备选方案。造错东西的代价比探索三个方案更高。

**规则**：正确答案不明显时，做 2–3 个相互竞争的原型或草图，并排比较，然后才投入。"设计两次"就是这条规则的另一个名字。第一个形状的另一个变体不算。

**适用于**：
- 新的 UI 交互（代码库里没有先例）。
- 有多种可行做法的架构选择。
- 用户体验取决于手感而非逻辑的产品设计决策。

**不适用于**：
- 模式已确立的机械实现。
- 目标状态明确的 bug 修复或重构。
- 约束只允许一种可行做法的改动。

## [P22] 先迁调用方，再删旧 API（migrate-callers-then-delete-legacy-apis）

**适用**：引入一个新的内部 API，而旧调用方还在时。

**内核**：一旦确定新 API 是正确的设计，就在同一波重构里迁移调用方并删除旧 API，而不是保留兼容层。

**规则**：
- 不要只因为内部还有调用方就保留旧 API 路径。
- 盘点调用方，迁移它们，立刻删除旧 API。
- 临时适配器是例外、要限期，不是默认架构。
- 更新测试去断言新契约；删掉只保护重构前实现细节的测试。

**前提**：
- 没有外部使用者依赖向后兼容。
- 项目能承受协调好的破坏性改动。
- 新 API 是某次简化或重构的一部分。

**为什么**：新旧 API 并存会制造双路径复杂度、拖慢清理，让代码库变得只增不减。

## [P23] 面向结果执行（outcome-oriented-execution）

**适用**：执行有明确阶段边界的计划性重写和迁移时。

**内核**：为预期的、可验证的终态做优化，而不是保住平滑的中间状态。

**为什么**：让每个中间步骤都完全稳定，往往要写临时兼容代码，而它会变成长期债务。向目标架构收敛，在明确的验证边界上证明正确性。

**核心规则**：
- 终态完整性优先于过渡期稳定性。
- 中间状态的破坏，只要是计划内的、限定范围的、可回退的，就可以接受。

**护栏**：
- 只用于有明确阶段边界的计划性重写和迁移。
- 事先声明哪里可以接受临时破坏。
- 迁移期间，对正在改动的区域保留高信号检查。
- 计划完成时要求完整的静态和运行时验证。

## [P24] 守住上下文窗口（guard-the-context-window）

**适用**：上下文正在被填满时：大输出、长文件、反复读取、规划 fan-out。

**内核**：上下文窗口是有限的，在一个会话里不可再生。每个 token 都要值它的成本。

**为什么**：上下文溢出会降低推理质量、制造压缩伪影、让进度停下来。

**做法**：
- **隔离大载荷。** 把冗长的输出、截图、大文档交给子 agent。主上下文只拿摘要，不拿原始数据。
- **常用内容内联。** 每次调用都要用的模板和参考，放进 skill 文件本身，而不是放进每次都要多读一次的单独文件。
- **给阶段定尺寸、给范围设上限。** 限制每个阶段的文件数，设定轮次预算，把机制本身的成本算进去。

## [P25] 实践取舍：TDD 与规格先行（spec-first）的关系

**适用**：决定用不用 TDD、或看到 tdd / test-first 类实践与本方法论的规格先行流程是否冲突时。

TDD（先写失败测试再写实现）在本方法论里是 **实现内层的编码节奏**，尤其用于修 bug（先写复现 bug 的失败测试）和改旧行为（characterization 测试）。规格（spec）的验收条件是 TDD 测试的靶子——先有规格定"做什么 + 验收"，TDD 再负责"打靶的红绿节奏"。两者嵌套，不互斥。

**不采纳** TDD 的"涌现式设计"（emergent design，设计从红绿循环里长出、不预先设计）——那与本方法论规格先行（设计由需求/规格/计划前置）对立。采纳的是 TDD 的编码节奏，拒绝的是它的"不预先设计"。
