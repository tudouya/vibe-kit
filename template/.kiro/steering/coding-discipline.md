# 编码执行纪律（coding-discipline）

steering-id: CD-646b

**适用**：本轮会真正产生代码改动时——新增或修改源文件、实现功能/接口、重构、修 bug、执行 AI-DLC 代码生成阶段。纯问答、读代码讲解、改文档或配置可忽略本规程。

**本规程被加载，说明你正要改动代码。动手前先过以下几关；每关都把一条已有信条细化成可执行动作，细节回查 `principles.md`。**

## [G1] 先证明"安全依赖的那个事实"，而不是口头断言

动手改之前，找出"这个改动之所以不出问题"所依赖的那一两个关键事实，并尽量用能跑的证据把它钉到最低一级（指到 `file:line` ＞ 走通失败路径 ＞ 跑一段真实代码）。一句"应该没问题"不算证据。
→ 信条：`prove-it-works`、`model-the-domain`。

## [G2] 写新逻辑先定核心类型 / 数据结构

若在写新代码，先把核心类型、数据结构、模块边界定对，再填实现。数据结构对了，下游实现大多是显然的；急着写实现会把错误的形状焊死。

细化（来自 architect）：
- **要穷尽设计空间时，候选必须是"整体形状不同"的方案，不是同一形状里的点修。** "换个字段名/多传个参数"不算第二方案——那只是同一设计的变体。拿不出结构上真正不同的另一个方案，就说明还没穷尽。
- **用"只看局部的下一个 agent"视角自检**：假设下一个改这里的人（或 agent）只看它打开的那几个文件、照抄最近的示例、走最短的能编译路径。你的设计要让"从单个文件看着对"的改动，对整个仓库也对。若一个改动只有看全局才知道对不对，这个形状就有坑。
→ 信条：`foundational-thinking`、`boundary-discipline`、`exhaust-the-design-space`。

## [G3] 改旧行为前先上锁

要改一段你（和模型）没完全看懂的现有行为前，先确认有安全网锁住现状：重构先写 characterization 测试，修 bug 先写能复现的失败测试；写完先确认它为"预期的那个原因"失败，而不是无关原因。没有安全网不要动遗留行为。

反向护栏（来自 tdd）——没有干净测试路径时，别硬写坏测试冒充安全网：
- 当测试路径不清、昂贵、要大量 mock、要慢的 e2e、要生产态、复现步骤模糊，或要大量无关 fixture 改动时，不要为"走完上锁这步"硬凑一个测试。
- 坏测试的特征（有其一就是坏测试）：主要在测 mock、编码的是当前实现细节而非预期行为、依赖时序或全局状态、为一个小修要搭重基建、证完这次就该删。
- 宁可不写测试，用最近的可执行验证兜底（针对性脚本、手动复现命令、快照比对、日志断言、聚焦的集成检查），也不要写坏测试——坏测试给的是假绿灯，比没有更危险。
- 这块确实缺真正的测试，就登记为可测试性债（`/td-tech-debt` 登记模式），不要假装"测试全绿"等于"这处改动安全"。
→ 信条：`lock-before-changing`、`test-behavior-not-implementation`。

## [G4] 收敛到目标形态，别留一次性兼容层

有明确目标架构的改写 / 迁移中，向目标收敛；需要时同一波迁移调用方并删旧接口，别用临时兼容代码保平滑中间态（但要显式声明本次的破坏范围）。
→ 信条：`outcome-oriented-execution`、`migrate-callers-then-delete-legacy-apis`。

## [G5] 实现中反复别扭，是信号——推翻重设计，别栓补丁

实现时若一再撞墙，先分清是"数据天生复杂"还是"设计错了"。下列是**设计错了**的可识别信号（是模式，不是单次个例）：
- 同一形状的 workaround 在不相关的地方反复出现；
- 多个互不相关的 edge case 都要加特判分支；
- 类型要靠逃生舱（`any`、cast、"实际总会有值"的可选字段）才能通过；
- 冒出"这里得加个锁"的念头，而当初设计说这块状态不共享；
- 填实现时出现两处以上同形状的、偏离原设计的改动。

看到这些**模式**，停下来推翻原设计重来，而不是继续往错形状上栓补丁。单个 edge case 不构成信号——用判断力。
→ 信条：`redesign-from-first-principles`、`fix-root-causes`。

---

**完成后**：对真实产物验证（跑功能 / 读实际值 / 查 diff），不靠自报"已完成"。做出权宜取舍时，提议登记技术债（`/td-tech-debt` 登记模式）。
